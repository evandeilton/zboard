What this dashboard measures, where the numbers come from, what they cannot support, and under which licence they are published.

Purpose

A static dashboard, updated daily and without a server, consolidating in one place the health of the R packages published on CRAN, their download history, development activity in the curated GitHub repositories, and the associated academic output. It serves two purposes at once: operational, detecting a CRAN regression before the official notification, and showcase, as a public portfolio artefact.

Methodology

A scheduled job collects each source independently once a day, writes the result to a typed, columnar store, and derives from it the JSON this page reads. A failing source degrades only its own section; the rest of the dashboard still publishes with the data available. Writes are idempotent by natural key, so re-running the pipeline on the same day does not duplicate a row. Only official APIs and artefacts are used: no HTML is scraped.

The set of packages and repositories is curated explicitly in config/repos.yml. Anything not listed there is not collected, not aggregated and not displayed: curation is an editorial decision, not a display filter.

Daily granularity is retained for a rolling twelve months; a monthly rollup is kept permanently. The rollup is written before any pruning, and pruning is aborted if the rollup fails, because repository traffic is the one series that cannot be reconstructed.

Only aggregates per package and per repository are published. No contributor profile, issue author or e-mail address is collected.

Declared limitations

Methodological transparency is a requirement, not a courtesy. The text below is normative and is published in both languages.

1. Downloads are not a census.

The series reflects exclusively the cloud.r-project.org (Posit) mirror. There is no known inclusion probability for the remaining mirrors; therefore no unbiased estimator of the total number of downloads exists. Use the series for relative trend, never as an absolute level.

2. Contamination by automation.

CRAN check farms, Docker images and third-party CI pipelines inflate the count. In niche packages, the non-human fraction may be the majority.

3. Release artefact.

Every new version produces a jump of several times the baseline, caused by the rebuilding of Windows and macOS binaries. The release markers on the chart exist to make that artefact visible — not to correct it.

4. Traffic with a truncated start.

The series begins on the date of the first collection; the period before it is inaccessible by design of the API.

5. Citations with a lag.

OpenAlex counts have an indexing latency of weeks to months and incomplete coverage for software.

What this dashboard deliberately does not do

No modelling, forecasting or anomaly detection. The dashboard is descriptive. CRAN download series are a convenience sample from a single mirror, contaminated by continuous integration and bots; modelling them would produce inference with no external validity.

No commit-count ranking or target as a headline indicator. The metric is subject to Goodhart’s law: it measures typing volume, not production. Commits appear only as a secondary series on the GitHub page.

No collection of identifiable third-party data. Contributor profiles and issue e-mail addresses are out of scope; only per-repository aggregates are published.
